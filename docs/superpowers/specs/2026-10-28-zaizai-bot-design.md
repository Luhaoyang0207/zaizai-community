# zaizai 社区机器人 — 设计说明（Spec）

日期：2026-10-28　状态：待你审阅
所有可调数值见 `docs/PARAMETERS.md`（本文不重复数值，只引用键名）。

## 1. 目标
为"玩家找队友"的 Discord 社区做一个功能比较全的机器人。玩家进入语音房间后发组队命令，机器人发卡片并维护总表。
成功标准：
- 玩家 `!pw` / `!pp`（含全角 `！`）后，立刻在其消息下看到卡片，总表里多一行条目。
- 房间空了、房主点"组队已满"、超时，条目自动从总表消失，总表始终是准确的。
- 高峰期（常有 99+ 个房间）不刷屏、不触发速率限制、不超过 Discord 的频道数量上限。
- 以后人多了，能把机器人按模式拆成多个，不用重写程序。

## 2. 术语
- **入口房间**：三个"创造 XX 房间"语音频道，玩家点进去会自动得到自己的临时房间。
- **临时房间**：机器人建出来的语音房间，空了就删。
- **卡片**：玩家发命令后，机器人发在其消息下面的那张消息。
- **条目**：信息组队总表里的一行。一个房间发一次组队，产生一张卡片和一个条目。
- **总表**：信息组队频道里，每种模式（排位/匹配/其他游戏）各一条固定消息，由机器人原地编辑。
- **面板**：临时房间建好后，机器人在房间自带的文字聊天里发的控制面板，@房主。

## 3. 范围
第一版包含：
1. 加入即创建的临时语音房间（排位、匹配、其他游戏三类）。
2. 组队命令、卡片、总表。
3. 房间面板，只有两个按钮：开/锁、组队已满。
4. 广告位、底部文字、"删除原消息"开关，可由指令修改。
5. 所有数值进配置文件，对应 `docs/PARAMETERS.md`。

第一版不包含（已延后）：
- 管理指令谁能用（管理员还是指定角色）——以后设计。
- 面板的"刷新面板"和"准星"按钮。
- 欢迎消息、角色分配等其他功能，以后作为新模块加入。

## 4. 架构
- 语言和库：Python，discord.py。
- 一份代码，一个进程。功能分成互相独立的模块：`voice_rooms`、`lfg`（命令和卡片）、`board`（总表）、`panel`（房间面板）、`ads`（广告位和文案）、`admin`（管理指令）。模块之间不互相调用内部实现，只通过一个共享的"状态层"和"事件"沟通。
- 状态存在本地 SQLite（记事本）：房间、条目、总表消息 ID、可改的设置。机器人重启后据此恢复。
- 配置：配置文件与 `docs/PARAMETERS.md` 的键名一一对应。令牌放在 `.env`，不提交到 GitHub。
- 需要在 Discord 开发者后台开启 Message Content Intent（读取 `!pw` 命令）。

### 拆分机制
- 配置里的 `modules.enabled` 和 `modules.mode_scope` 决定一个机器人实例负责哪些功能、哪些模式。
- 拆分 = 在 `docker-compose` 里加一个服务，用同一份代码、新令牌、新配置。
- 每个实例用**自己的 SQLite 文件**，不共用。
- 每个模式有自己的入口房间、分类和总表消息，所以按模式拆分不需要机器人之间通信。
- 实例只处理自己负责的模式，避免两个机器人同时回应同一条命令。

## 5. 数据（SQLite）
- `rooms`：房间 ID、模式、房主、创建时间、是否锁住、面板消息 ID。
- `entries`：条目 ID、房间 ID、模式、需求文字、发起人、卡片消息 ID、创建/更新时间。
- `board_messages`：模式、总表消息 ID（可能有多条）。
- `settings`：可由指令修改的值（广告位、底部文字、各频道的删除开关）。

## 6. 流程

### 6.1 临时房间
1. 玩家进入入口房间 → 机器人在对应分类里新建房间，名字按 `voice.name_template`，把玩家移进去，设为房主，在房间聊天里发面板（@房主）。
2. 分类满了（`voice.category_max_channels`，Discord 上限 50）→ 自动新开一个分类继续放。
3. 房间空了 → 等 `voice.empty_delete_delay_sec` 秒后**直接删除**，不复用（`voice.reuse_empty_rooms=false`）。
4. 建房、删房请求排队（`voice.create_queue_interval_ms`）。建房不是主要瓶颈。

### 6.2 组队命令
1. 玩家在对应文字频道，或房间自带聊天里，发命令。全角 `！` 同样识别。房间聊天里的命令，模式由房间所在分类决定。
2. 检查：玩家不在语音房间 → 提示先进语音，不发卡片。命令和频道模式不匹配 → 忽略。发送间隔由 Discord 慢速模式控制，机器人不单独限制。
3. 发卡片，位置是玩家消息下方：需求、总表入口链接、发起人和时间、广告位、底部文字。
4. `card.delete_original` 打开时，删除玩家的原消息。
5. 同一个房间再次发命令 → 更新原条目，不新增第二条。
6. 在总表里新增或更新条目。

### 6.3 总表
- 每种模式一条固定消息，原地编辑。每个条目：需求、发起人、时间、跳转到卡片的链接、"人数 @ 房间名"的进房按钮。按最新在前排序。
- 无条目时显示 `board.empty_text`。
- 人数变化等事件合并后刷新，最多每 `board.refresh_debounce_sec` 秒编辑一次。
- 一条消息放不下时拆成多条（每条上限 `board.max_entries_per_message`，实际上限写代码前查证 Discord 当前限制）。
- 条目消失的条件（任一满足）：房间空了、房主点"组队已满"、房间被删、超过 `board.entry_timeout_min` 分钟没更新。
- 条目消失后，卡片**保留不处理**（`card.after_entry_end=keep`）。
- 总表消息被人手动删了 → 下次刷新时重新发一条并记录新 ID。

### 6.4 面板
- 按钮：🔓开/🔒锁（锁住后别人不能再加入，已在房间的人不受影响）、组队已满（移除该房间的条目）。
- 房主没有其他权限（不能改名、改人数、踢人）。
- `/panel` 可以重新召唤面板。

### 6.5 重启恢复
启动时对照记事本和服务器里的真实房间与消息：清掉记事本里已不存在的房间和条目，认领仍存在的，重建缺失的总表消息，并立即刷新一次总表。

## 7. 限制与风险
- Discord：每个分类最多 50 个频道，整个服务器最多 500 个。临时房间多时必须自动分类。
- 一条消息能放的按钮、组件数量有限，决定每条总表消息的条目数；写代码前查证当前数值。
- 总表和卡片的编辑、发送是主要的速率压力点，已用合并刷新缓解。
- 记事本文件需要放在 Docker 挂载目录，否则重建容器会丢失。
- 令牌不得进入仓库；本地测试和线上使用不同的机器人令牌和不同的服务器。

## 8. 错误处理
- 缺权限：日志写明缺什么，并在管理频道提示一次。
- Discord 暂时出错：重试几次，仍失败则跳过本次，不让进程退出。
- 手动删除了总表、卡片或面板：容错，不报错，必要时重建。

## 9. 测试
- 自动测试（不连 Discord）：命令识别（含全角）、条目生命周期（各种消失条件）、排序与分页、分类溢出、重启恢复的对账逻辑。
- 手动测试：本地 Docker + 测试机器人 + 测试服务器，走一遍建房、发命令、总表刷新、锁房、组队已满、重启。

## 10. 部署
- Docker 镜像，一个容器一个机器人。VPS 上用 `docker-compose`，本地测试也用 Docker。
- 挂载目录：配置、SQLite 数据文件。令牌通过 `.env` 注入。

## 11. 已延后的开放项（不阻塞第一版实现）
- 管理指令的权限范围（管理员 / 指定角色）。
- "其他游戏"频道的命令写法（排位 `!pw`、匹配 `!pp` 已定）。
- 广告位和底部文字的具体内容。
- 临时房间默认人数上限。
- "刷新面板"和"准星"按钮。
